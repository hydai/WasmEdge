## Findings

### #1 — Memory leak in `unsafeUnregisterModule` — FIXED

| | |
|---|---|
| **File** | `lib/vm/vm.cpp` |
| **Line** | 275 |
| **Severity** | High — affects every unregister call |
| **Status** | Fixed in `10759cfd5` |

**Summary**: `unsafeUnregisterModule` leaks the `ModuleInstance` and leaves a
dangling null slot in `RegModInsts`.

**Detail**: The `RegModInsts` branch does `(*InstIt).release()` + `terminate()`
but never `delete`s the raw pointer and never erases the vector element. The
`BuiltInModInsts` and `PlugInModInsts` branches just below correctly call
`.erase(It)`.

**Failure scenario**: Each unregister leaks the `ModuleInstance` (destructor
never runs: `unlinkAllStores`, `HostDataFinalizer`, dependency in-degree
decrement all skipped) and accumulates a null `unique_ptr` slot that every
subsequent `hasLiveInstanceWithID` / `cleanup` must skip. Repeated
register/unregister cycles grow the vector unboundedly.

**Fix**: Added `RegModInsts.erase(InstIt)` after `release()`, matching the
`BuiltInModInsts` and `PlugInModInsts` branches.

### #2 — Null deref in `runCallOp` — FIXED

| | |
|---|---|
| **File** | `lib/executor/engine/controlInstr.cpp` |
| **Line** | 164 |
| **Severity** | High — segfault in lazy-JIT mode |
| **Status** | Fixed in `ae1ecd63f` |

**Summary**: `runCallOp` calls `checkLazyCompilation(FuncInst)` on a
potentially-null pointer from `getFuncInstByIdx`.

**Detail**: `getFuncInstByIdx` returns `nullptr` when the top frame is a dummy
frame (`helper.cpp:374`). `checkLazyCompilation` immediately dereferences
`FuncInst->isWasmFunction()` (`executor.h:1161`) with no null check. In
interpreter/AOT mode `CompTrigger` is null so the `&&` short-circuits; in
lazy-JIT mode (`CompTrigger != null`) the null deref is a segfault.

**Failure scenario**: In lazy-JIT mode, a call executed under a dummy/null-module
top frame makes `getFuncInstByIdx` return `nullptr`; `checkLazyCompilation` then
dereferences null at `executor.h:1161` and segfaults. The existing `*FuncInst`
deref in `enterFunction` on the next line was the pre-existing crash site; the
new `checkLazyCompilation` moves the crash earlier and into a lazy-JIT-only
regression.

**Fix**: Added `FuncInst &&` to the condition chain in `checkLazyCompilation`
(`executor.h:1161`). This also resolves finding #5 (`runCallRefOp`) since both
call sites share the same helper.

### #3 — `const_cast` UB when lazy-JIT mutates caller's const Module — FIXED

| | |
|---|---|
| **File** | `lib/vm/vm.cpp`, `include/vm/vm.h` |
| **Line** | 230 (also 385) |
| **Severity** | High — undefined behavior per the C++ standard |
| **Status** | Fixed in `0645e623d` |

**Summary**: `const_cast<AST::Module&>(Module)` is UB when the original object
is const, and `prepare()` mutates it via `loadExecutable`.

**Detail**: `registerModule(name, const AST::Module&)` `const_cast`s the module
before passing to `onModuleRegistered`. In lazy-JIT mode `prepare()` calls
`LoaderEngine.loadExecutable(Module, JITLib)` which writes
`Module.setSymbol()` — modifying an object whose original may be const. The same
`const_cast` appears at line 385 (`runWasmFile` path).

**Failure scenario**: A caller passing a genuinely `const AST::Module` (allowed
by the public API signature) triggers undefined behavior per `[dcl.type.cv]`. In
practice this usually "works" but can be miscompiled — the compiler may assume
the const object is unchanged and cache stale reads.

**Fix**: Added non-const overloads of `registerModule` and `runWasmFile` that
work directly with mutable modules (no copy, no cast). The const overloads now
deep-copy the module before forwarding so the caller's original is never
mutated. The internal `unsafeRegisterModule` and `unsafeRunWasmFile` take
`AST::Module&` (non-const) and no longer need `const_cast`. Also made
`prepare()`'s idempotent fast-path call `loadExecutable` on a module copy whose
symbol is not yet set, so that copies arriving via the const overload bind the
function-type wrappers from the shared dylib.

### #4 — Missing strategy hook on `ModuleInstance` register — FIXED

| | |
|---|---|
| **File** | `lib/vm/vm.cpp` |
| **Line** | 248 |
| **Severity** | Medium — lazy JIT silently disabled for pre-built instances |
| **Status** | Fixed in `0645e623d` |

**Summary**: `registerModule(Name, const ModuleInstance&)` skips the strategy
hook entirely, silently disabling lazy JIT for pre-built instances.

**Detail**: This overload calls only `ExecutorEngine.registerModule` with no
`Strategy->onModuleRegistered()`. In LazyJIT mode, no `LazyJitManager` state is
prepared for the instance's ID. A pre-built `ModuleInstance` carries no
`AST::Module`, so lazy compilation cannot be enabled — but the user receives no
indication that their instance will run interpreted.

**Failure scenario**: At execution, `ensureCompiled` -> `compileFunction` finds
no `States` entry (`lazy_jit_manager.cpp:149-155`) and silently returns `{}` —
every call into that module runs in the interpreter forever with no diagnostic.
The instance is also not pushed to `RegModInsts`, so `hasLiveInstanceWithID`
cannot see it, and a later unregister of a wasm module sharing that ID may drop
shared lazy state the host instance depends on.

**Fix**: Added an `spdlog::info` diagnostic when a pre-built `ModuleInstance` is
registered in lazy-JIT mode (`Strategy->needsCompilationTrigger()`), explicitly
stating that its wasm functions will run in the interpreter because no AST module
is available for compilation.

### #5 — Potential null deref in `runCallRefOp` — FIXED (by #2)

| | |
|---|---|
| **File** | `lib/executor/engine/controlInstr.cpp` |
| **Line** | 185 |
| **Severity** | Medium — same pattern as #2, lower trigger likelihood |
| **Status** | Fixed in `ae1ecd63f` (same fix as #2) |

**Summary**: `runCallRefOp` calls `checkLazyCompilation(FuncInst)` where
`FuncInst` from `retrieveFuncRef` may be null.

**Detail**: The preceding null check at line 176 only rejects a null
`RefVariant`, not a null return from `retrieveFuncRef`. `proxyCallRef`
(`proxy.cpp:216-219`) guards the identical `retrieveFuncRef` result with an
explicit `if(unlikely(!FuncInst)) return AccessNullFunc` before calling
`checkLazyCompilation`; this interpreter path does not.

**Failure scenario**: If `retrieveFuncRef` yields `nullptr` for a non-null but
dangling/corrupt ref, `checkLazyCompilation` dereferences null
(`executor.h:1161`) in lazy-JIT mode. Lower severity than #2 since a non-null
funcref normally resolves, but the asymmetry with `proxyCallRef`'s explicit guard
shows the intended contract is to null-check `retrieveFuncRef` before use.

**Fix**: The `FuncInst &&` null guard added to `checkLazyCompilation` in #2
covers all call sites, including this one.

### #6 — `isWasmFunction()` invariant silently broken after lazy upgrade (PLAUSIBLE)

| | |
|---|---|
| **File** | `include/runtime/instance/function.h` |
| **Line** | 149 |
| **Severity** | Medium — latent, any new code using the old invariant is wrong |

**Summary**: After lazy upgrade, `isWasmFunction()==true` AND
`getCompiledCodePtr()!=nullptr` simultaneously, breaking the old
mutually-exclusive variant invariant.

**Detail**: `unsafeUpgradeToCompiled()` now stores into
`LazyCompiledSymbol`/`LazyCompiledCode` and leaves `Data` holding `WasmFunction`
untouched. The old `isCompiledFunction()`/`isWasmFunction()` were mutually
exclusive; that contract is silently gone.

**Failure scenario**: Any code that branches on `isWasmFunction()` to mean
"interpreted-only" is now wrong. `stacktrace.cpp:86` uses
`isWasmFunction() && !getCompiledCodePtr()` correctly, but the invariant change
is undocumented and a future reviewer-added `isWasmFunction()`-only check would
misroute a JIT-compiled function to the interpreter.

### #7 — `getLazyCompiledFuncCount()` bypasses `VM::Mutex` (PLAUSIBLE)

| | |
|---|---|
| **File** | `include/vm/vm.h` |
| **Line** | 302 |
| **Severity** | Low — the only public accessor that violates the locking discipline |

**Summary**: `getLazyCompiledFuncCount()` reads
`Strategy->compiledFuncCount()` with no `VM::Mutex` lock, unlike every other
public accessor.

**Detail**: The `LazyJitManager`'s own `shared_mutex` protects the `States`
traversal, so the count itself won't tear. But this accessor is the only public
method that violates the class's locking discipline.

**Failure scenario**: If a future `cleanup` ever reassigned the `Strategy`
`unique_ptr`, or `VM` is destroyed while another thread reads the count,
`Strategy->compiledFuncCount()` dereferences a dangling pointer. Even today it
is the lone accessor that breaks the uniform shared-lock convention.

### #8 — Global mutex serializes all lazy compilation across modules (EFFICIENCY)

| | |
|---|---|
| **File** | `lib/vm/lazy_jit_manager.cpp` |
| **Line** | 147 |
| **Severity** | Medium — scalability bottleneck |

**Summary**: `compileFunction` holds a single global `unique_lock` across the
entire LLVM compile and JIT add, serializing all lazy compilation across all
module IDs.

**Failure scenario**: Thread A triggers a large batch compile (dozens of
functions, tens of ms of LLVM codegen). Thread B's first call into an unrelated
module blocks in `compileFunction`'s `unique_lock(Mutex)` until A's full LLVM
codegen finishes. The expensive, side-effect-free compilation steps
(`BatchCompiler.compileFunctions` on private `LLVM::Data`) could run outside the
lock, turning a global serialization point into per-module contention.

### #9 — Redundant double atomic load per function call in lazy-JIT mode (EFFICIENCY)

| | |
|---|---|
| **File** | `lib/executor/helper.cpp` |
| **Line** | 145 |
| **Severity** | Low — hot-path overhead in steady state |

**Summary**: In lazy-JIT mode, `getCompiledCodePtr()` is loaded twice per
function call — once in `checkLazyCompilation`, then again in `enterFunction`.

**Failure scenario**: Every `call`/`call_ref`/`call_indirect` in lazy-JIT mode
pays two atomic-acquire loads for a function that is already compiled (the steady
state after warmup). `checkLazyCompilation` could return the resolved code
pointer so `enterFunction` reuses it instead of re-loading.

### #10 — AOT functions pay unnecessary atomic acquire load (EFFICIENCY)

| | |
|---|---|
| **File** | `include/runtime/instance/function.h` |
| **Line** | 99 |
| **Severity** | Low — affects AOT hot path |

**Summary**: `getCompiledCodePtr()` always performs an atomic acquire load of
`LazyCompiledCode` first, even for AOT functions that will never use it.

**Failure scenario**: An AOT-compiled module executes a tight call-heavy loop.
Every compiled-call dispatch issues an atomic acquire load that is structurally
always null for AOT, then falls through to the `holds_alternative<Symbol>`
branch. AOT functions are constructed via the `Symbol` constructor and never
upgraded; the lazy slot is permanently null. The ordering could be relaxed for
AOT, or the lazy slot consulted only for native `WasmFunction` variants.

### #11 — Six parallel lock-step vectors are fragile (CLEANUP)

| | |
|---|---|
| **File** | `lib/vm/lazy_jit_manager.cpp` |
| **Line** | 217 |
| **Severity** | Low — maintainability risk, not a current bug |

**Summary**: `compileFunction` maintains six lock-step parallel vectors
(`ToCompile`, `ToCompileGlobals`, `ToCompileInsts`, `ExistingGlobals`,
`ExistingInsts`, `ExistingAddrs`) with no structural tie.

**Failure scenario**: Six containers indexed by a shared position with no
compiler-enforced linkage. `ToCompileGlobals` is pure redundancy (every element
equals `ImportFuncCount + ToCompile[i]`). A future edit that pushes to one
branch vector but forgets a sibling desynchronizes the indices; the `Wire` loop
at 333-338 then pairs a `FunctionInstance` with the wrong code address and
publishes wrong machine code into a function. Collapsing into two struct vectors
would make this impossible.
